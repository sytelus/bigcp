We wish to create a brand new command line tool called bigcp that will work in Windows. Currently, there is robocopy utility available on Windows but it still gets very slow when it encounters too many small files. It seem to require different options for efficient large file copy and yet other options for network copy etc. It has been often observed that in these variety of conditions robocopy achieves very suboptimal throughput. Our tool is going to overcome these issues. Our tool will also exclusively target modern SSDs and magnetic hard drives. It will take advantage of design, architecture and properties of these drives to maximize the throughput. Additionally the tool may judiciously use threads, proper APIs, fast data streaming, large bursts, large buffers, techniques such as async io, hardware details on individual drives, characteristics of USB-C connections or anything else that may be applicable, useful or relevant to maximize the throughput when it is possible. It will also take advantage of modern machines such as current PC with many cores, new gen PCIe bus, USB-C connection, huge amount of RAM (at least 32 GB but often 64 GB) and so on. You may investigate various read and write methods that allows maximizing throughput for SSD and HDD while connected via USB-C. Our tool must be efficient, robust and extremely reliable. You will only use official APIs and/or reliable or proven libraries. You may chose any suitable language including C++, Rust or Python. The tool must not miss copying files or copy them incorrectly or partially or in corrupt way because of bugs.

There is no need to implement full suit of arguments as in robocopy or other tools to keep things simple and maintainable. The tool should use defaults that is expressed by following robocopy arguments: /E /J /COPY:DTA /DCOPY:DATE /R:0 /W:0 /V /FP /ETA /SJ /SL. Additionally, our tool will be optimized for SSDs and HDDs and primarily USB-C as well as machines with many cores and very large RAM. Again, to keep things simple, there is no need to implement optimizations for other scenarios (such as networked copy, old OS or old machines) and you may assume this is our primary case. Network locations are out of scope entirely: the tool should work only with local volumes and should reject network (UNC) paths upfront with a clear error. Since no-retry is the default behavior, there is no need to offer any retry arguments; failed files are addressed by simply re-running the tool. Overall, the argument surface of the tool should remain minimal.

The tool must provide beautiful modern terminal based UX with colors, formatting, progress and variety of information that may be useful and let users know what is going on. You may decide to build dashboard kind of UX if needed and if it is more useful. The tool should be able to resume more or less at same point if it was abruptly or intentionally terminated and re-run. The tool must avoid re-copying files if they already exist at destination. You may review how robocopy and other tools use fast and efficient heuristics to determine if source and destination files were same and, if there are opportunities, improve on them. The tool must produce log file that can be programmatically parsed. The tool should be conscious about not producing unnecessary disk io. The tool should offer verification in exactly two forms and no more: an option that, once copying completes, verifies the files that were copied during that run, and a standalone mode that fully verifies the source tree against the destination tree. A single fast hash algorithm (for example, xxHash3-128) is sufficient wherever hashing is needed; the goal is detecting accidental corruption, omissions and such bugs but not protection against deliberate tampering, so multiple or cryptographic hash choices are unnecessary.

It may happen that file copy generates errors. The tool should log those errors and provide some running tally of errors, why are they happening and perhaps some hints to resolve them in next re-run when possible. Files that cannot be read due to permissions should simply be reported as failures with a helpful hint; there is no need for a special backup-privilege mode to force-copy them.

We may expect very large files (40GB or more) and if partial file resume is  useful then algorithms and code must ensure that such files are handled carefully, (for example, as temp file or some other scheme) so it is not mistaken as completed and verification is performed to provide confidence for integrity after restart.

When destination file is detected to be different and decision is to overwrite, it should be logged accordingly with appropriate information for later analysis and showing summary statistics.

You may assume that we will have 1. Windows 11 22H2 or later versions so you can use advanced modern better APIs and simplify things.

Only NTFS and ReFS volumes are supported, for both source and destination; exFAT, FAT32, and any other filesystems are out of scope and should be rejected upfront with a clear error. Any advantage NTFS and ReFS offer for performance and reliability should be taken.

The tool should have exactly one copy engine of its own. Alternative engines built on OS copy APIs are not product features, although they may be used inside the test harness to validate correctness. Likewise, special-case acceleration for copies within the same volume (such as ReFS block cloning) is not needed because the primary scenario is copying between drives; it is fine, however, to inform the user when the OS itself could perform such a same-volume copy faster.

To simplify things, you may assume exclusive stable source tree. Similarly, you may assume that destination tree is also available to you exclusively and stable. You may add detection for violation for these assumptions if it doesn't add copy performance overhead (RAM or CPU overhead is ok).

The tool should avoid copying system files by default such as System Volume Information, and paging files. It should always notify which files would be and were excluded and argument should be provided to turn this off.

Simple pre-allocation may be used where it helps performance, provided reliability goals are not violated. SetFileValidData and similar mechanisms that require special privileges or can expose stale disk data must not be used; the small throughput gain is not worth the risk.

Prompting to user in middle of copy should be avoided and tool should use arguments instead. In the same spirit, when a run is interrupted — by errors, a disconnected device, or the user — the tool should stop safely, and re-running it should resume the work; abort-and-rerun is the only recovery model needed. In-run recovery interactions, such as waiting for a device to be reconnected, are not needed.

Add argument to allow replacements when destination file differs (default is true).

For Alternate Data Streams and Extended Attributes consider the fact that they may not exist most of the time and so optimizations may be possible.

There is no need to carry over file system compression feature to destination is that impacts performance. For sparse layout, we should attempt to maintain it on destination when supported to avoid unnecessary cost in storage.

Any unit tests or other tests must be confined to specific new folders in order to avoid unintentional changes or data loss or any other harm on any existing files or folders on the drives due to running those tests. A careful review of all tests must be performed to ensure they do not alter anything outside of their designated folders. Additionally, all tests including stress tests or any other performance tests must ensure drives such as SSDs or HDDs does not get damaged or corrupt in any way or aggressively written to which would shorten their lifespans. All tests of any kind must be harmless.

Do not over-optimize for this specific PC in general although you can assume availability of many cores and large RAM and recent PCIe generation and USB-C connection. You should make choices for algorithms considering the fact that a PC may have variety of HDDs and SSDs of varying generations (connected as either internal drive or external drive via USB-C) and therefore it is best to rely on general performance characteristics of these hardware rather than characteristics of disks on this specific PC. Make sure any gates or tests takes this into consideration. Accordingly, it is sufficient to choose performance settings statically from the well-known characteristics of each class of drive, with arguments available for manual override; the tool does not need to adaptively re-tune itself while a copy is running. However, this does not prohibit implementation to do any minor measurement and adaption to adjust settings like QD/stream count especially to make sure they are within safe bounds.

The tool should comfortably handle huge numbers of files and directories overall. For any single directory, it is sufficient to optimize for up to about one million entries; even larger directories may be processed more slowly but must still be handled correctly.

There is no need to monitor disk temperatures in this version; reporting observed throughput behavior, including slowdowns, is sufficient.

You may assume and enforce only one run for the exact destination root per machine to simplify things.

Last-access time copy is best-effort/informational. Last-access can be captured and set when an object is copied, but not used for skip equality because reading and external activity can change it.

To keep the tool simple, the following are also not needed: separate device probing or benchmarking options (throughput observed during the run is a sufficient basis for reporting); options to record file hashes beyond what verification and resume integrity require; detection or reporting of hard links (copying each linked file as an independent file is acceptable); and volume-level flushing (when a durable flush option is provided, per-file flushing suffices).

Above everything, reliability is the most important goal for this tool. This means when tool says X was successfully copied and Y failed, user can be sure that is indeed correct and that file paths, content, attributes are correct. However, tool should strive to avoid unnecessary checks that may reduce throughput. The tool should never corrupt files or delete them when they also didn't exist in source as it will cause data loss. The tool should also not produce any extra files that user didn't expect. The tool must treat source strictly as read-only (except for generating log or reports or temporary files if source drive is specified for those purposes). The tool should produce summary of how many files were successfully copied, how many failed, breakdown of failures by top level folders and reason, throughput achieved, best observed sustained throughput and so on. In terminal UX, user should be able to navigate and examine more details about different aspects of your report. User should be able to also invoke tool latter with report file as argument to re-examine report at later date. The report should include any other useful details such as throughput bottlenecks, time started, time ended, slowest portion, fastest portion, any hints to improve throughput for next run when possible and so on.

Your job is to first review all current techniques to maximize copy throughput while taking advantage of modern hardware such as current machine and then design complete algorithm, architecture and implementation for the tool that will be reliable, robust and maximize the throughput while dealing with variety of circumstances such as huge number of very small files, very large files, tons of directories, source and destination drives with mismatched speeds and so on. You will study existing techniques to deal with these various scenarios and when necessary create your own techniques or improve upon existing ones. You will also thoroughly study various edge cases implemented in other code basis and make sure you cover them in bigcp when they are relevant. You may also examine various reliable and popular open source projects which might have some success with the same goals. Your plan will include architecture, implementation details, finer points of everything, reasoning for your choices, test plan for various scenarios as well as catching potential robustness and reliability bugs and anything else you think that may be important or helpful. You will also include guidance on document to create and instructions on maintainable code so any future maintainer can maintain it without having to ask any questions to anyone. Your plan should have all the necessary details so an engineer can faithfully and reliably implement your vision and intention. However, plan does not need to include development phases or timeline or team coordination or such human management details. You will save this plan in PLAN.md.
