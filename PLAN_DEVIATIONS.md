# Plan deviations

- **Invariant I5 is implemented as “a final name appears only after all file data and streams are complete,” with final timestamps and attributes applied immediately after rename.** PLAN.md §4.3 requires metadata to be set after rename to defeat NTFS name tunneling, while I5 says metadata is already complete before the rename. Both orderings cannot hold simultaneously. The implementation follows the normative completion sequence in §4.3; the brief post-rename metadata window remains recoverable because an interrupted file is classified as different and recopied.
- **Dry-run does not create a missing destination root.** PLAN.md §4.5 requires creating and pinning a missing destination during pre-flight, while §10.1 promises that `--dry-run` performs zero destination-tree writes. The zero-write safety promise takes precedence: dry-run pins the nearest existing ancestor, validates the prospective destination path, and models the absent tree without creating it.
- **The initial pre-1.0 large-file path is bounded, buffered, synchronous streaming rather than the planned IOCP + unbuffered overlapped ring.** Shipping unsafe overlapped state machinery without the plan's sans-I/O completion model, fault-site injection, cancellation race coverage, and chaos soak would be unwise under VISION.md's reliability priority. Chunk sizing, sparse range transfer, offset-ordered hashing, exact checkpoints, stream promotion, preallocation, and the common atomic finalizer are implemented, so an IOCP transport can replace the bounded read/write port without changing semantics. `--no-unbuffered` is retained for grammar compatibility but has no effect until that transport lands; no v1.0 performance claim is made.
- **Named-stream discovery uses the correct path-based `FindFirstStreamW`/`FindNextStreamW` API rather than parsing `FileStreamInfo` on an already-open object handle.** Source identity is revalidated immediately around discovery, and every actual directory/reparse/temp stream handle is opened non-following, so current copy semantics remain safe and complete. This costs an extra path-based metadata operation, leaves per-stream allocation size unavailable, and creates a small stability-assumption window. Replacing it with the plan's variable-length handle query requires a carefully bounded unsafe parser plus malformed-record and concurrent-mutation coverage; adding that parser without those tests would be unwise in the reliability pass.
- **Checkpoint boundaries use deterministic size tiers from 256 MiB through 4 GiB instead of estimating roughly five seconds from live throughput.** Exact-boundary digest snapshots and resume integrity are implemented; only checkpoint frequency differs. A traffic-rate controller would be misleading while the current large-file transport is synchronous and the richer ETA/governor telemetry is deferred, so adaptive boundary timing belongs with that scheduler work.
- **Queue-depth and concurrent-stream profile fields are reported and range-validated but are not yet active I/O concurrency controls.** The current streaming transport has one synchronous large/sparse transfer at a time while the bounded worker pool handles small files. Treating configured QD as actual device utilization would be misleading, so the UI labels only measured application rates. Activating QD/stream controls is coupled to the IOCP work above.
- **Enumeration/join and large-file execution are coordinator-driven, and small-file workers perform their own final close instead of feeding a separate finalizer pool.** The queues and worker set are bounded, but the plan's parallel enumerators, per-device scheduler, and Defender-amortizing close stage are performance hypotheses that require the missing isolated benchmarks and chaos coverage before their additional ordering and lifetime complexity is justified. The common atomic finalizer remains the only publication path, so these future transports do not require a semantic rewrite.
- **The bounded passive governor, Restart Manager lock-owner lookup, device/space circuit breakers, free-space forecast, and million-entry spill/fallback are deferred pre-1.0.** None is needed for semantic correctness, and implementing or claiming them without their specified simulations and large-directory tests would create unverified failure paths. Current failures remain per-object and auditable; fatal orchestration errors stop the run. These items remain release work, not silently claimed features.
- **The query-only profiler currently supplies topology extents, bus class, seek penalty, transfer length, and sector alignment, but not vendor/model strings, hotplug/removal-policy inference, device write-cache state, or physical-RAM discovery.** The missing facts are not used to make current correctness decisions; confidence falls back conservatively and the report avoids claiming physical-device utilization. Adding the remaining IOCTL parsers requires bridge-specific fixtures and the hardware/VHDX matrix, so their UI and hint fields remain release work.
- **Opening a new ADS requires a micro-window in which delete-on-close is cleared on the opaque temporary.** Windows rejects a new stream open while the base file is delete-pending. The implementation clears the disposition for only the stream-open syscall and re-arms it before returning the stream handle. A kill in that window can strand an opaque `.bigcp-…part`, but can never expose a partial final name or alter an old destination; the artifact is reported rather than deleting anything unproven. Keeping every possible ADS handle open in advance would be unbounded and is therefore worse.
- **ReFS publication is implemented with `FileRenameInfoEx` but has not passed the plan's elevated ReFS capability/probe matrix.** The current machine allowed only harmless C: NTFS sandbox testing; falsely declaring ReFS replacement certified would be unwise. A ReFS cell must validate POSIX/ignore-readonly flags and add a capability-gated legacy atomic rename fallback before v1.0 certification.
- **Post-copy `--verify` currently verifies every file written by the run, including unnamed data, named streams, EAs, masked attributes, creation time, and last-write time, but does not add directories or reparse objects to that run-local read-back queue.** Standalone `bigcp verify` and the independent oracle do cover the complete file/directory/reparse/tree contract. Extending the run-local target model without the missing reparse/VHDX and fault matrix would create an unvalidated second object-verification path; v1.0 must either add those target types or narrow the plan's statement. Both verification forms currently use buffered reads, so they do not claim the plan's cache-defeating unbuffered verification property.
- **Standalone `bigcp verify` returns and prints the full-tree `VerificationSummary`, but does not yet persist that result in the copy-run report schema; `VerifyOptions.report_path` is reserved and currently unused.** Forcing a read-only comparison into fields that describe a copy run would produce misleading counters, profiles, and lifecycle data. Before v1.0, the report schema needs an explicit verification-only run kind (or a separate versioned verification artifact), after which the CLI can expose its report path without inventing copy activity.
- **Destination-only named streams on an existing directory are preserved and reported as verification divergence rather than deleted.** PLAN.md requires stream-set fidelity, while the no-delete contract forbids removing unexpected destination data without a separately authorized destructive policy. Source streams are created or replaced and all reparse-object streams are carried through replacement temps, but exact convergence of a pre-existing directory with extra ADS requires manual resolution or a future explicit policy.
- **The live/report TUI is intentionally a compact, truthful pre-1.0 dashboard rather than the full interaction design in PLAN.md section 11.** It provides bounded nonblocking snapshots, tabs, throughput, counters, grouped failures, report reopening, bottleneck evidence, and hints, but not predictive ETA, sparklines, per-transfer progress, expandable error trees, theme persistence, or the complete keyboard/navigation surface. An ETA before full discovery and active concurrent streaming would be misleading; the remaining presentation work depends on stable scheduler telemetry and snapshot/interaction coverage.
- **Unrecoverable audit failure currently aborts immediately and joins/drops bounded workers instead of producing the plan's best-effort final report after a separately modeled drain state.** Continuing unaudited would be worse, and committed files remain valid while uncommitted owned temps self-delete, but the richer drain/report behavior needs deterministic log-device fault injection. Similarly, journal-invalidated or `--fresh` persistent partials are never blindly deleted, but the planned ownership-proven orphan scan, ten-run retention cleanup, and cleanup hints are not yet implemented; opaque leftovers can consume space until manually reviewed.
- **The plan's `tracing`-span rule is not implemented as a second telemetry stack.** Versioned JSONL already records every terminal file outcome, non-file error, warning, profile, and statistics sample with lossless paths; adding parallel spans without the specified hidden debug grammar, subscriber policy, and overhead measurements would create two competing audit narratives. If diagnostic spans are added, JSONL remains the source of truth and release builds must demonstrate that disabled spans have no hot-path cost.
- **Invariant I10 is enforced by the core call graph, read-only source capability types, root containment checks, and tests rather than by a source-root-aware refusal inside every `bigcp-win` write constructor.** The platform crate intentionally also serves the testkit, which must create source fixtures, and its current destination primitives do not carry a product-run root token. A future backend extraction should introduce an unforgeable destination capability rooted at the pinned destination handle; doing so now would be a broad API rewrite without changing the currently audited product call sites.
- **The full test/release matrix is documented but not fabricated or executed here.** Fault injection at every Win32 site, 30-minute/8-hour chaos, disposable VHDX NTFS/ReFS/exFAT cells, `CopyFile2`/robocopy differential copying, million-entry and 20 GiB workloads, performance regression floors, and the real-hardware checklist require dedicated runners, elevation, long execution, or explicitly designated scratch hardware. Running them on existing drives would conflict with VISION.md's harmless-test requirement and the user's explicit ban on F:, G:, and H:. The code is labeled pre-1.0 until these gates exist and pass.
- **Fixed competitor multipliers are treated as aspirational metrics, not current release facts.** PLAN.md itself records that the numbers are unvalidated; enforcing them without topology-matched baselines would make correctness contingent on arbitrary hardware/controller behavior and encourage endurance-heavy retesting. `BENCHMARKS.md` starts with no certified claim and requires evidence-derived per-class floors.
- **The testkit currently provides the safe marker, bounded deterministic file generator, and independent full tree/stream/EA oracle, but not `oscopy` or `chaos` subcommands, one YAML scenario for every E-case, or the plan's allocation/sentinel snapshot around the destination boundary.** Those checks depend on the missing differential/fault infrastructure and a harness-owned before/after snapshot rather than an oracle invoked only after copy. The included smoke scenario and end-to-end tests intentionally write only a few MiB on a new C: sandbox; structural final-path/reparse containment remains mandatory for every current operation.
