# High-confidence improvements to `PLAN.md`

- **P0 — Process rolling hashes in file-offset order.** The streaming engine hashes buffers as read completions arrive, but overlapped reads may complete out of order (`PLAN.md` §5.9 and §6.3). Feeding those buffers directly to XXH3 or BLAKE3 calculates the hash of completion order, not file order. Add an ordered hash-commit cursor such as `next_hash_offset`; completed chunks wait in the bounded reorder window until all preceding chunks have been hashed. Checkpoint watermark `W` must not advance until hashing is contiguous through `W`, and adversarial tests should assert the exact digest, not merely monotonic watermarks.

- **P0 — Move durable-mode flushing after rename and metadata application.** The current completion sequence flushes the temporary file before rename and timestamp/attribute changes (`PLAN.md` §4.3), yet durable completion promises the final namespace and metadata survive power loss (`PLAN.md` §7.5). The durable sequence should be: finish data → rename → set EOF/timestamps/attributes → flush the final file → attempt a volume-level flush. Also report `requested`, `file-flush-achieved`, and `volume-flush-achieved`, because flushing an entire volume requires administrator privileges and hardware does not universally honor cache-flush semantics. [Microsoft's `FlushFileBuffers` documentation](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers) documents the privilege requirement; [`CreateFile2` documentation](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/ns-fileapi-createfile2_extended_parameters) explicitly warns that not all hardware supports write-through correctly.

- **P0 — Resolve the `/DCOPY:DATE` versus EA contradiction.** The plan promises `/DCOPY:DATE`, but deliberately drops extended attributes even when the destination can represent them (`PLAN.md` §4.2 and §13). This also contradicts the rule that a file counts as copied only when all representable metadata is present (`PLAN.md` §4.4). Either implement file and directory EA copy in v1, or change the requirement to `/DCOPY:DAT`. Microsoft documents EAs and alternate streams as backup stream types through [`WIN32_STREAM_ID`](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-win32_stream_id), accessible using [`BackupRead`](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-backupread); this is preferable to making undocumented native `Nt*` APIs part of the public design.

- **P0 — Include ADS/EAs in classification, verification, and the oracle.** A file can presently be classified `Same` from unnamed-stream size/mtime even when an alternate data stream is missing or corrupt. The plan then never schedules its ADS pass. Define a stream-set fingerprint or a separate stream-reconciliation state, and require full verification to compare stream names, lengths, and contents. Directory ADS and EAs require the same treatment. Microsoft's [`COPY_FILE_DIRECTORY`](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-copyfile2_extended_parameters_v2) can preserve directory streams, EAs, and reparse information on the supported Windows target, providing a useful differential baseline.

- **P0 — Do not describe XXH3 equality as proof of byte identity.** The resume protocol says equality "proves" the prefix is identical (`PLAN.md` §5.12), but XXH3 is explicitly a [non-cryptographic hash](https://github.com/Cyan4973/xxHash). Either use [BLAKE3](https://github.com/BLAKE3-team/BLAKE3) for checkpoint integrity or describe XXH3 as high-confidence accidental-corruption detection rather than proof. Given the reliability emphasis and hundreds-of-gigabytes resume case, BLAKE3 is the cleaner choice.

- **P0 — Put every optimized backend behind one semantic finalizer contract.** ReFS cloning and CopyFile2 bypass the normal source-read/hash path, yet the plan says every large file receives a source digest and post-read validation (`PLAN.md` §5.9 and §5.11). Specify that all backends must return a common result containing source pre/post metadata, copied stream set, final identity, and digest availability. A clone should not claim an in-flight source digest unless it actually reads the source; copying ADS, timestamps, commit revalidation, and logging must still run through the common finalizer.

- **P0 — Choose a coherent policy for audit-log failure.** The logging section allows copying to continue with `audit:"degraded"` (`PLAN.md` §5.15), while invariant I7 still calls the log sink "infallible-by-buffering" and promises every failure is logged (`PLAN.md` §7.1). Continuing after losing the only complete machine-readable log cannot satisfy F7/I7. Recommended behavior: stop dispatching new work after the reopen attempt fails, finish already-in-flight operations, write the best available fallback report/stderr summary, and exit 6.

- **P1 — Make overlapping-run exclusion genuinely atomic and machine-wide, or narrow the guarantee.** The exact-root global mutex plus `%LOCALAPPDATA%` registry (`PLAN.md` §5.12) cannot see other Windows users and does not atomically serialize registry scans for different-but-overlapping roots. Use a short-lived global coordinator mutex around registration/conflict detection and a shared machine-readable registry with appropriate ACLs, while retaining per-root lifetime locks. Alternatively, explicitly guarantee only same-user or exact-root exclusion.

- **P1 — Define startup when the destination root does not yet exist.** Root identity checks say both roots are opened and pinned (`PLAN.md` §4.5), but a normal new destination cannot be opened. Resolve and pin the nearest existing destination ancestor, validate each missing component without following unexpected reparses, create the root, then pin and revalidate its final identity before enumeration begins.

- **P1 — Reconcile the destination reparse threat model with the adversarial tests.** The plan disclaims protection against hostile tree mutation but also claims it never writes through an unexpected destination reparse and tests junction swaps during a run (`PLAN.md` §4.5 and §12.4). Path-based validation followed by path-based creation has a TOCTOU window. Either use handle-relative component opens and writes rooted at pinned directory handles, or narrow E36 and the guarantee to reparses present at classification time.

- **P1 — Add a separate metadata-memory budget and bounded large-directory join.** Per-directory source arrays, destination hash maps, and a global file-ID set can consume multiple gigabytes for the promised three-million-entry directory, outside the buffer-pool limit (`PLAN.md` §5.6 and E25). Define a metadata high-water mark and a fallback such as external sort/spill, batch lookup, or per-source destination probes. Hardlink statistics should not require an unbounded global identity set.

- **P1 — Fix the overwrite-confirmation timing.** A prompt based on more than 1,000 replacements or 100 GiB (`PLAN.md` §10.1) cannot be shown reliably once streaming enumeration has already dispatched writes. Choose one of: a preflight pass, explicit `--replace` authorization, or a prompt at the first replacement. The current threshold design and one-pass execution cannot both hold.

- **P1 — Make timestamp preservation testable, including last-access time.** The plan sets last-access time but intentionally excludes it from equality because it may drift. Clarify the exact guarantee: capture the source timestamp snapshot before reading, apply creation/write/access times after content and rename, and record whether each projected destination value was successfully set. Creation and last-write timestamps should remain strict for files and directories; last-access can be excluded from skip classification, but standalone verification should report it separately rather than silently ignoring it.

- **P1 — Move compression and sparse layout out of the correctness baseline.** The reference copier still must implement sparse-layout and compression preservation (`PLAN.md` §13), contrary to the clarified scope. Logical contents must remain correct, but sparse allocation and compression should be optional optimizations that enter the native engine only after an isolated benchmark demonstrates a material win. If NTFS compression is used, configure it before writing instead of performing a potentially expensive recompression after the copy.

- **P1 — Correct filesystem and device-profile claims.** The fixed "16 EB" limits (`PLAN.md` §4.4) do not reflect Windows-supported ReFS/NTFS limits; Microsoft currently documents different supported maxima in the [ReFS overview](https://learn.microsoft.com/en-us/windows-server/storage/refs/refs-overview) and [filesystem comparison](https://learn.microsoft.com/en-us/windows/win32/fileio/filesystem-functionality-comparison). Prefer "filesystem/configuration-dependent" except for the actionable FAT32 4 GiB limit. Also, `IOCTL_STORAGE_GET_HOTPLUG_INFO` exposes surprise-removal/hotplug characteristics, not a definitive "Quick removal versus Better performance" policy; its write-cache override field is reserved. Report this as an inference with `unknown` support, consistent with Microsoft's [`STORAGE_HOTPLUG_INFO`](https://learn.microsoft.com/en-us/windows/win32/api/winioctl/ns-winioctl-storage_hotplug_info).

- **P1 — Convert unmeasured performance assertions into hypotheses and gates.** Examples include metadata revalidation having "no disk I/O," checkpoint flushing costing below 1%, XXH3 using below 2% of a core per GB/s, universal flush behavior, and deferred close giving a proven 3× gain (`PLAN.md` §5.8 and §5.12). Keep the mechanisms, but express these numbers as hypotheses to validate in `BENCHMARKS.md` on the target hardware.

- **P1 — Repair the performance-ceiling methodology.** `min(independent source-read ceiling, independent destination-write ceiling)` is not a valid ceiling when both sides share a controller, USB hub, filesystem, or physical device (`PLAN.md` §8.7). Measure a topology-matched simultaneous read/write ceiling. The cold-cache protocol also remounts only the destination, leaving source caching uncontrolled; use datasets larger than RAM or define a reproducible source-cache reset.

- **P2 — Remove remaining internal contradictions and stale terminology.** Specific fixes include:

  - Replace the claim that delayed buffered-write errors are reliably caught by `CloseHandle`; close is not a durability barrier (`PLAN.md` §5.8).
  - Change "No hash unless requested" because large-file hashing is always enabled (`PLAN.md` §8.4).
  - Replace Unix "kill -9" with `TerminateProcess` (E17).
  - Replace "exact shortfall" with estimated/range-based shortfall (E15).
  - Define tracker `pending` as child directories plus every scheduled file/link/metafix outcome; `|children|` is ambiguous (`PLAN.md` §6.2).
  - Explain how descendants are enumerated and accounted when destination-directory creation fails; `account_subtree` cannot know unseen descendants in a one-pass walk (`PLAN.md` §6.2).

- **P2 — Separate elevated filesystem tests from ordinary CI.** Creating, mounting, formatting, and testing VHDXs generally needs an elevated/self-hosted Windows runner, and ReFS availability depends on the Windows edition/configuration. Label the VHDX matrix accordingly instead of simply "CI-able" (`PLAN.md` §12.5); keep pure state-machine, fault-injection, and model tests in ordinary CI.

Recommended: separate the streaming threshold from the resume-checkpoint threshold. A 4 MiB file benefits from streaming but usually does not justify durable journal checkpoints every few seconds. Enable checkpoint resume only above a much larger configurable threshold, potentially 8–40 GiB, based on measured restart savings. This aligns better with the stated 40 GiB+ use case and avoids flush overhead on ordinary files.

Recommended: preserve timestamps strictly but define last-access separately. Creation and last-write times for files and directories should remain mandatory. Last-access time should be captured and set, but either treated as “preserved at completion” rather than a stable equality key, or verified and restored explicitly. This avoids endless recopy churn without weakening the useful timestamp guarantee.

Recommended: retain two explicit durability levels rather than trying to maximize speed and power-loss durability simultaneously. Keep logical completion as the fast default and provide --flush as best-effort durable completion with reported capability. If power-loss survival becomes mandatory by default, accept that small-file throughput will fall and change the primary metric accordingly.

Keep logical completion as the fast default and provide --flush as best-effort durable completion with reported capability. In case of scenario such as Power-loss or abrupt termination, it is acceptable that some files will be incomplete but this must be detectable in next re-run and fixed.

Recommended: make source-change detection subject to a measured overhead budget. The current wording assumes metadata revalidation is effectively free. State an acceptable overhead, such as under 1–2% on the small-file benchmark; if it exceeds that, retain post-read validation for replacements/large files and expose stricter detection as an option.
